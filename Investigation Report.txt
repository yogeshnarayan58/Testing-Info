## 1. NEW FILE: `e2e/utils/safe-path.ts`

**Before**: did not exist.

**After** (full file):
```typescript
import * as path from 'path';

/**
 * Joins `baseDir` with a single dynamic filename segment, guaranteeing the
 * resolved path can never escape `baseDir` (defense against path traversal /
 * "Unsanitized dynamic input in file path" SAST findings).
 *
 * - Strips any directory components from `fileName` via `path.basename()`.
 * - Resolves both `baseDir` and the joined path to absolute form and verifies
 *   containment before returning.
 *
 * Throws if the resolved path would fall outside `baseDir` (this should be
 * unreachable in practice once `path.basename()` has stripped `..`/`/`, but
 * the explicit check gives SAST tools a verifiable containment guarantee at
 * the sink itself, independent of how the filename was produced upstream).
 */
export const safeJoin = (baseDir: string, fileName: string): string => {
  const resolvedBase = path.resolve(baseDir);
  const safeName = path.basename(fileName);
  const resolvedPath = path.resolve(resolvedBase, safeName);

  if (resolvedPath !== resolvedBase && !resolvedPath.startsWith(resolvedBase + path.sep)) {
    throw new Error(`Unsafe path resolution detected for filename: ${safeName}`);
  }

  return resolvedPath;
};
```

**Cycode finding addressed**: none directly (this is the new shared helper consumed by the
fixes below) — it exists to give every fs sink in the three files below the same
containment guarantee.

**Reasoning**: All three flagged files already sanitized the *filename* upstream (regex
strip via `safeTestId`/`sanitizeId`, or `path.basename()`), yet Cycode kept flagging the
`fs.writeFileSync`/`fs.readFileSync` sink itself. This indicates the SAST rule tracks taint
from source to sink and does not treat ad-hoc regex `.replace()` calls as a recognized
"path sanitizer" — it wants the containment check to happen right at (or immediately
before) the sink. `safeJoin()` centralizes that: it re-derives the basename (defense in
depth even if a caller forgets to pre-sanitize) and then explicitly resolves + verifies the
result is inside `baseDir` before returning, which is the standard OWASP path-traversal
mitigation pattern (canonicalize, then verify containment) and the kind of check SAST tools
are built to recognize as a real sanitizer.

## Approach Summary

**Sanitization pattern used, and why**: a single shared helper, `safeJoin(baseDir,
fileName)` in `e2e/utils/safe-path.ts`, that (1) strips any path components from the
filename via `path.basename()` and (2) resolves both the base directory and the joined
path to absolute form and verifies the result is still contained under the base directory,
throwing if not. This is the canonical OWASP path-traversal mitigation
("canonicalize, then verify containment") and was chosen specifically because Cycode kept
flagging sinks even though the filenames were already sanitized upstream (via regex
`.replace()` or bare `path.basename()`) — those existing sanitizers evidently aren't
recognized by the rule as clearing taint on their own. Doing the containment check
immediately at the `fs.*` call gives the analyzer (and any future reviewer) a
self-contained, verifiable guarantee at the sink itself, independent of what happened
upstream.

**Existing pattern reference vs. new code**: I first checked repo memory
(`/memories/repo/tooling-gotchas.md`), which references a prior
`e2e/CYCODE_FINDINGS_REVIEW.md` worked example covering these same three files — but that
file does not currently exist in the workspace (likely from an earlier session that never
persisted it), so there was no existing `safeJoin`-style helper to reuse. I did keep the
existing sanitization idioms already present in this codebase untouched (`safeTestId`
regex strip in `base-page-factory.ts`/`lt-session-reporter.ts`, `sanitizeId()` in
`globalTeardown.ts`, `path.basename()` on directory-listing results) — `safeJoin()` is
layered on top of those as an additional sink-side check, not a replacement.

I also explicitly checked the sibling `disc-fe-omnishopper-ui-automation` repo (also open in
this workspace) for an equivalent shared sanitization utility, since it has near-identical
`lt-session-reporter.ts` / `globalTeardown.ts` files
(`src/lib/playwright/reporters/lt-session-reporter.ts`,
`src/lib/playwright/setup/globalTeardown.ts`) and a `base-page-factory.ts`
(`src/lib/common/utils/base-page-factory.ts`) — clearly the origin/sibling of this repo's
LambdaTest reporting code. Searching that repo (`grep` for `safeJoin`, `sanitizePathComponent`,
`resolvedBase`, `containment`, `path.resolve`, and the existing `src/lib/common/utils/*.ts`
files: `page-utils.ts`, `locator-utils.ts`, `env-utils.ts`, `element-utils.ts`,
`assert-utils.ts`) turned up **no equivalent shared path-safety utility**. The only related
prior art there is the same *inline, per-call-site regex sanitization* idiom already used in
this repo — e.g. `common-test-case.ts` (screenshot path construction) does:
```typescript
// Sanitize dynamic inputs to prevent path traversal and file system attacks
// Only allow alphanumeric, hyphens, and underscores in path components
const sanitizedReportName = reportName.replace(/[^a-zA-Z0-9-_]/g, "-").toLowerCase();
const sanitizedBrowserName = browserName.replace(/[^a-zA-Z0-9-_]/g, "-").toLowerCase();
const sanitizedTestCaseName = testCaseName.replace(/[^a-zA-Z0-9-_]/g, "-").toLowerCase();
const sanitizedEnvironment = environment.replace(/[^a-zA-Z0-9-_]/g, "-").toLowerCase();

const screenshotPath = path.join(
  "baseline-screenshots",
  sanitizedReportName,
  sanitizedBrowserName,
  datasetShort,
  sanitizedEnvironment,
  `${sanitizedTestCaseName}.png`
);
```
and OmniShopper's `globalTeardown.ts` uses the exact same `path.basename(file)` pattern this
repo's `globalTeardown.ts` already had before my change. Every `path.resolve()` occurrence
in that repo (`base-page-factory.ts`'s `storage/auth.json`, `testResultsReader.ts`'s
`DEFAULT_REPORT_PATH`) is only ever used to resolve a **static** path against
`process.cwd()` — none of them re-verify containment of a dynamic/user-influenced segment
the way `safeJoin()` does.

**Conclusion**: `safeJoin()`/the resolve-then-verify-containment pattern is **new** —
written from scratch based on the general OWASP path-traversal mitigation guidance, not
copied or adapted from any existing utility in either repo. It does not match or duplicate
anything already in OmniShopper's codebase; it's a stricter pattern than what either repo
had, introduced specifically because Cycode kept flagging the pre-existing
regex-sanitization-only approach as insufficient.

**No runtime behavior change — confirmation**:
- `safeJoin()` is behaviorally a no-op wrapper for every call site it was added to: in all
  cases `baseDir` (`sessionDir` from `getLambdaTestSessionDir()`, or `ALLURE_RESULTS_DIR`)
  is already an absolute path (`path.join(process.cwd(), ...)`), and every dynamic filename
  passed in (`test-${safeTestId}.json`, `worker-${workerIndex}.json`,
  `test-${safeTestId}-${process.pid}-${Date.now()}.json`, or an already-`path.basename()`'d
  directory-listing entry) contains no `/`, `\`, or `..` segments. For such inputs,
  `path.resolve(path.resolve(baseDir), path.basename(fileName))` is identical to
  `path.join(baseDir, fileName)` — same absolute string, same file written/read, same value
  passed into every subsequent `console.log`/JSON payload. The `safeJoin()` throw path is
  only reachable if a filename ever *did* contain traversal sequences, which none of the
  call sites can produce.
- I did not change any of `sessionName`, `testId`, `workerIndex`, `sanitizedFile` derivation
  logic, JSON payload shapes, or log message text/format — only comments were updated (to
  describe the new `safeJoin()` guarantee) and the `path.join(...)` call was swapped for
  `safeJoin(...)` at each dynamic-filename sink.
- Verified via `get_errors` (no TypeScript diagnostics) and `npx tsc --noEmit` on the `e2e`
  project (clean, no output) after the change — confirming the refactor type-checks
  correctly. A full `playwright test` run could not be exercised in this sandbox (per
  `/memories/repo/tooling-gotchas.md`: no LambdaTest network egress / no live-site
  credentials here), so behavior equivalence was verified by static/type-check plus the
  path-equivalence reasoning above rather than an end-to-end run.
