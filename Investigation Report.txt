# Investigation: Dynamic File-Path Handling — `disc-fe-omnishopper-ui-automation` vs `disc-fe-omni-survey-mod/e2e`

**Date:** 2026-08-21
**Scope:** Read-only investigation. No files were modified, no security scanners were run.
**Goal:** Determine whether `disc-fe-omnishopper-ui-automation` has the same category of
"Unsanitized dynamic input in file path" (Cycode SAST / CWE-73 / CWE-22 family) code as
`disc-fe-omni-survey-mod/e2e`, and whether they have solved it.

---

## Summary / Verdict

**Yes — Omni Shopper has the same category of dynamic-path code, and no, it does not have an
equivalent `safeJoin()` / validation utility.** Their code is essentially the *pre-hardening*
version of our own files (same architecture, same filenames, same variable names in several
places), with only light, inconsistent character-filtering in a couple of spots and **zero**
path-containment/boundary checks anywhere. There is no evidence in their code that they have
resolved this finding — it looks unaddressed.

---

## 3. Would their pattern trip the same Cycode rule?

Yes. The Cycode "Unsanitized dynamic input in file path" rule (CWE-73/CWE-22 family) flags any
`fs.*` / `path.join` / `path.resolve` sink fed by a runtime-derived value without a recognized
sanitizer chain. Omni Shopper's:

- `base-page-factory.ts` (`testId`, `workerIndex` — completely raw)
- `lt-session-reporter.ts:36` (`testId` — completely raw)
- `global-setup.ts` (`file` from `readdirSync` — completely raw, most exposed of all)

are **at least as exposed as our pre-fix code was**. Their `globalTeardown.ts` and
`common-test-case.ts` do have partial mitigations (`path.basename()`, `startsWith`/`endsWith`
filters, regex allowlisting), but none match Cycode's expected "resolve + boundary-check" shape
that our `safeJoin` / `assertContainedDir` implements — SAST tools typically still flag
`path.basename()`-only or denylist-only patterns because they don't verify the *final resolved
path* stays inside a trusted root.

---

## 4. Do they have an equivalent of our `safeJoin()` / `safe-path.ts`?

**No.** There is no `safe-path.ts`, `safeJoin`, `assertContainedDir`, or any shared
path-validation utility anywhere in `disc-fe-omnishopper-ui-automation`. Each file does its own
ad-hoc, inconsistent partial sanitization (or none at all):

- `global-setup.ts` → no sanitization whatsoever
- `base-page-factory.ts` → no sanitization whatsoever
- `lt-session-reporter.ts` → sanitizes in one place (line 101), not in another (line 36)
- `globalTeardown.ts` → `path.basename()` + suffix/prefix string checks only
- `common-test-case.ts` → character-allowlist regex only, no path resolution/boundary check

## 5. Our project's reference implementation (for context)

Our `e2e/utils/safe-path.ts` exports two helpers used across
`utils/base-page-factory.ts`, `playwright/setup/globalTeardown.ts`, and
`playwright/reporters/lt-session-reporter.ts`:

- **`safeJoin(baseDir, ...untrustedSegments)`** — rejects empty segments, NUL bytes, traversal
  sequences (`..`, `~`, backslashes, absolute paths, both POSIX and Windows-style, OS-agnostically);
  allowlist-sanitizes each segment to `[a-zA-Z0-9_.-]`; resolves symlinks on the base dir via
  `fs.realpathSync`; joins and re-resolves the final path; and verifies the result still starts
  with the resolved base directory before returning it.
- **`assertContainedDir(expectedRoot, dir)`** — verifies a directory value (e.g. from
  `getLambdaTestSessionDir()`) resolves inside `expectedRoot` before it is trusted as a base for
  further `fs` operations.

This is the "resolve + boundary-check" pattern that is **entirely absent** from
`disc-fe-omnishopper-ui-automation`.

---

## Conclusion

Omni Shopper has the same category of dynamic-path code (test IDs, worker indices, and
directory-listing filenames flowing into `fs.readFileSync`/`writeFileSync`/`readdirSync`/
`unlinkSync`/`path.join` calls) as our project had before hardening. There is **no evidence**
they have solved the equivalent Cycode finding — no shared validation utility, no
resolve+containment checks anywhere, and at least one location (`global-setup.ts`) with zero
sanitization of any kind on a `readdirSync` → `unlinkSync` path. It appears unresolved /
unaddressed in their repository.
