# TC_BS_08 (Point Scale) — Index & Component Investigation (Round 2)

Read-only report. No code changes made.

## 1. Does Point Scale's question-text input use the same `question-text-input-${index}-input` pattern?

**Confirmed via source — yes, identical binding pattern to Single Choice and NPS.**

`libs/survey-mod-lib/src/lib/features/build-survey/components/question-editor/scale-editor/scale-editor.component.html`
(used by both Point Scale and Multi Scale):
```html
<niq-text-field (valueChange)="onInputChange($event)" class="w-100 text-field question-field" [attr.data-test-id]="'question-text-input-' + questionNumber()"
    [value]="question()" [autofocus]="true" size="medium" placeholder="Question"
    [enhancedComponent]="true" [textOverflow]="'ellipsis'">
</niq-text-field>
```

Compared directly against the other question-type editors in the same directory:

`choice-editor/choice-editor.component.html` (Single/Multiple Choice):
```html
<niq-text-field class="text-field question-field" [attr.data-test-id]="'question-text-input-' + questionNumber()" [value]="question()" [autofocus]="true" ...>
```

`nps-editor/nps-editor.component.html` (NPS):
```html
<niq-text-field class="w-100 text-field question-field" [attr.data-test-id]="'question-text-input-' + questionNumber()" (valueChange)="onInputChange($any($event))" ...>
```

**All three use the exact same binding expression: `'question-text-input-' + questionNumber()`.**
Since NPS's rendered attribute was already confirmed via DevTools to be
`question-text-input-4-input` (the `niq-text-field` Athena-core component itself appends the
trailing `-input`), the same must hold for Point Scale/Multi Scale given the identical binding —
this part of our locator (`questionTextInput`) is correctly shaped for Point Scale.

## Critical finding: what `questionNumber()` actually resolves to for a NEW question

`question-editor.component.ts` (the parent wrapping all type-specific editors):
```ts
displayQuestionNumber = computed(() =>
  this.questionNumber() ?? this.upcomingQuestionNumber
);

get upcomingQuestionNumber(): number {
  return this.surveyService.getQuestions().length + 1;
}
```

`question-type-selector.component.html` (the component used while a NEW question is being
actively created, before it's saved — this is what our `clickQuestionTypeResource()` interacts
with):
```html
<survey-question-editor #questionEditor [selectedType]="selectedType()" [isPreview]="true"
    ...
    (discardChangesRequested)="discardQuestion()"></survey-question-editor>
```
**No `[questionNumber]` input is bound here.** This means, for the question currently being
created (not yet saved), `questionNumber()` is `undefined`, so `displayQuestionNumber()` falls
back to `upcomingQuestionNumber` — **`this.surveyService.getQuestions().length + 1`**, i.e. **the
live count of already-saved questions on the persisted survey, plus one, evaluated at the moment
the new question type is selected.**

**This means the correct `questionIndex` to pass is NOT a fixed sequence number derivable purely
from test file order — it is whatever `(current saved question count) + 1` is on the live,
persisted survey at the moment each test runs.** If the persisted survey ever has extra/missing
questions relative to what the test suite assumes (manual test runs, partial failures leaving
stray questions, etc.), this number shifts and any hardcoded value can silently become wrong.

  today may not be correct on the next run if the survey state changes again (manual edits,
  partial test failures leaving stray questions, etc.). A hardcoded `questionIndex` is inherently
  fragile against this persisted, shared survey — this is a structural risk, not just a one-off
  wrong number.
