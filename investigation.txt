## Collision analysis: static id vs. per-type vs. per-question id

The Phase 5 proposal for `choice-editor.component.html` used a **static**
id: `data-test-id="question-text-input"`.

**That static id would collide, and a per-type suffix (`-nps`, `-scale`)
would not fully fix it either.** Reason: `<survey-question-editor>` (which
wraps `choice-editor` / `nps-editor` / `scale-editor` / etc.) is instantiated
**once per question**, inside the `@for (q of questions(); ...)` loop in
[preview-mode.component.html](../../libs/survey-mod-lib/src/lib/features/build-survey/components/preview-mode/preview-mode.component.html#L11).
Multiple question cards render simultaneously on the Build Survey screen, and
a real survey commonly has **more than one question of the same type** (e.g.
two Single Choice questions, or two NPS questions) all mounted at once. So:

- A single static id per editor type (`question-text-input`,
  `question-text-input-nps`, `question-text-input-scale`) would still
  collide as soon as **two questions of the same type** are both on screen —
  which is the common case, not an edge case.
- The correct fix is a **dynamic, per-question** id, not a per-type static
  one. Each of the three editors already receives `questionNumber()` as an
  input signal (visible in all three templates above as
  `{{ questionNumber() }}.`), which is unique per question and is the
  natural key to use.

**Recommendation:** use `[attr.data-test-id]="'question-text-input-' + questionNumber()"`
in all three editors (`choice-editor`, `nps-editor`, `scale-editor` — this
also revises the Phase 5 static proposal for `choice-editor`, which should be
updated to match this dynamic pattern rather than staying static). This keeps
one consistent, collision-free naming convention across all question-type
editors regardless of how many questions of a given type are present.
