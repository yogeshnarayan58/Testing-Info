## PART 1 — Dataset selection

### 1. `searchAndSelectDataset()` — current implementation (start-from-scratch.page.ts)

```typescript
async searchAndSelectDataset(searchTerm: string, datasetLabel: string, _datasetIndex: number): Promise<void> {
  try {
    // Check-before-click: no locator exists for "a dataset tile is already selected" —
    // the closest confirmed signal is whether the "Choose a dataset" screen is still
    // showing at all. If it's gone, a dataset must already be selected — skip search.
    const chooseDatasetBreadcrumb = this.webActionHandler.getWebElement(
      this.resourceManager.getResource('chooseDatasetBreadcrumb', START_FROM_SCRATCH_PAGE_COMPONENT_NAME)
    );
    const isOnDatasetScreen = await chooseDatasetBreadcrumb.isVisible();
    if (!isOnDatasetScreen) {
      console.log('↷ "Choose a dataset" screen not shown — assuming already selected, skipping search');
      return;
    }

    // Check-before-search: the 'defaultDataset' element (confirmed "default-dataset-selected"
    // class) reflects whatever dataset was previously chosen. It may not exist at all if
    // nothing was ever selected — that's treated as "not matched", not an error.
    const defaultDatasetElement = this.webActionHandler.getWebElement(
      this.resourceManager.getResource('defaultDataset', START_FROM_SCRATCH_PAGE_COMPONENT_NAME)
    );
    const defaultDatasetText = await defaultDatasetElement.getText().catch(() => '');
    const isDefaultDatasetAlreadySelected = defaultDatasetText.trim().toLowerCase().includes(datasetLabel.trim().toLowerCase());
    if (isDefaultDatasetAlreadySelected) {
      console.log(`↷ Dataset "${datasetLabel}" already selected as default — skipping search`);
      return;
    }

    // Check-before-search: if the desired dataset tile is already visible on the
    // unfiltered list, skip the search-toggle/search-input steps entirely and click it.
    const existingDatasetElement = this.webActionHandler.getWebElement(
      this.resourceManager.getDynamicResource('datasetByLabel', datasetLabel, START_FROM_SCRATCH_PAGE_COMPONENT_NAME)
    );
    const isDatasetAlreadyVisible = await existingDatasetElement.isVisible().catch(() => false);
    if (isDatasetAlreadyVisible) {
      console.log(`↷ Dataset "${datasetLabel}" already visible — skipping search, clicking directly`);
      await existingDatasetElement.click();
      return;
    }

    const searchToggle = this.webActionHandler.getWebElement(
      this.resourceManager.getResource('searchToggle', START_FROM_SCRATCH_PAGE_COMPONENT_NAME)
    );
    await searchToggle.waitFor(SMALL_TIMEOUT);
    await searchToggle.click();

    const searchInput = this.webActionHandler.getWebElement(
      this.resourceManager.getResource('searchInput', START_FROM_SCRATCH_PAGE_COMPONENT_NAME)
    );
    await searchInput.waitFor(SMALL_TIMEOUT);
    await searchInput.enterText(searchTerm);
    await this.webActionHandler.delay(UI_STATE_UPDATE_DELAY);

    const datasetElement = this.webActionHandler.getWebElement(
      this.resourceManager.getDynamicResource('datasetByLabel', datasetLabel, START_FROM_SCRATCH_PAGE_COMPONENT_NAME)
    );
    await datasetElement.waitFor(SMALL_TIMEOUT);
    await datasetElement.click();
  } catch (error) {
    throw new Error(`Failed to search and select dataset "${datasetLabel}": ${error instanceof Error ? error.message : error}`);
  }
}
```

### 2. `panelist-flow.helper.ts` — target pattern (full file)

```typescript
import { BasePage } from '@gfk/gta';
import { SelectPanelistPage } from './select-panelist.page';

type DimensionSelectionsArg = Parameters<SelectPanelistPage['setDimensionSelections']>[0];

export async function completePanelistSelectionFlow(
  basePage: BasePage,
  dimensionSelections: DimensionSelectionsArg
): Promise<boolean> {
  const selectPanelistPage = new SelectPanelistPage(basePage);
  await selectPanelistPage.setDimensionSelections(dimensionSelections);
  await selectPanelistPage.clickSearchForPanelists();
  await selectPanelistPage.click250Responses();
  await selectPanelistPage.clickProceedToSurveyBuilder();
  return selectPanelistPage.isBuildSurveyPageLoaded();
}
```

### What `searchAndSelectDataset()` currently does, step by step

1. Reads `chooseDatasetBreadcrumb` — if the "Choose a dataset" screen isn't showing at all, **returns silently** (`void`), assuming a prior selection already happened.
2. Reads `defaultDataset` text — if it already matches `datasetLabel`, **returns silently**.
3. Checks if the target dataset tile (`datasetByLabel`) is already visible unfiltered — if so, clicks it and **returns silently**.
4. Otherwise, clicks `searchToggle` → types into `searchInput` → waits → clicks the resolved `datasetByLabel` element.
5. Any thrown error along the way is caught and re-thrown as a new `Error` with a `Failed to search and select dataset "<label>"` message.
6. Return type is `Promise<void>` in every branch — there is no way for the caller to distinguish "already selected, skipped" from "searched and selected" from "did nothing because it detected an unexpected state." The only two outward-visible outcomes are "resolved" (silently, regardless of which of the 4 branches ran) or "threw."

### Gap vs. `panelist-flow.helper.ts`'s shape

`completePanelistSelectionFlow()` is a **standalone exported function** (not a page-object method) that:
- Takes a `BasePage` and constructs its own page object instance inside the function.
- Chains several *void*-returning page-object action calls (`setDimensionSelections`, `clickSearchForPanelists`, `click250Responses`, `clickProceedToSurveyBuilder`) which all just perform clicks/fills and throw on failure — no branching, no early-return decisions.
- Ends by calling one *boolean-returning verification* method (`isBuildSurveyPageLoaded()`) and returns that boolean directly to the caller. It does not itself `expect()`/assert anything — the caller (the spec file) is expected to do `expect(await completePanelistSelectionFlow(...)).toBe(true)` or similar.

To match that shape, `searchAndSelectDataset()` would need to change in kind, not just detail:

- **Return type**: `Promise<void>` → `Promise<boolean>`. Every one of the current early-return branches (`return;`) would instead need to `return true`/`return false` based on an actual verified outcome, not just "we didn't throw."
- **Where assertion logic lives**: today the method makes its own decisions internally (breadcrumb gone → assume done; text matches → assume done) and never proves the end state — it just stops acting. In the boolean-return pattern, the *action* function stays dumb (do the search/click, don't decide if it "worked"), and a separate boolean *verification* step (comparable to `isBuildSurveyPageLoaded()`) would need to exist and be called at the end, with the caller asserting on it. Right now there is no equivalent "isDatasetSelected()"-style check being surfaced to the caller — the closest thing (`isDatasetSelectionConfirmed()`, checking the breadcrumb) exists elsewhere in the file but isn't wired into `searchAndSelectDataset()`'s return value.
- **Extraction boundary**: `panelist-flow.helper.ts` lives outside the page object as a free function orchestrating several page-object calls end-to-end (dimension selection → search → responses → proceed → verify). `searchAndSelectDataset()` today is one method *inside* the page object doing selection-only work with its own internal skip-logic — it isn't an orchestrator of multiple page-object steps, and nothing currently calls it plus a follow-up verification together as a single exported flow function.
- **Caller responsibility shift**: currently the spec/test calling `searchAndSelectDataset()` cannot `expect()` anything from it (it returns `void`) — the test must be relying on subsequent steps failing/passing to indirectly reveal whether dataset selection worked. Matching the target pattern means the spec would gain an explicit `expect(result).toBe(true)`-style assertion after the call, which doesn't exist today.

I have not written this extraction — flagging only the structural gap as requested.

## PART 2 — Navigate / base URL

### 1. `CommonPage` (full file — `e2e/page-objects/common/common-page.ts`)

```typescript
/**
 * Common base page object for this project's page objects.
 *
 * Mirrors Omni Shopper's CommonTestCase (src/lib/common/pages/common-test-case/common-test-case.ts):
 * initializes webActionHandler/resourceManager from BasePage in the constructor and exposes a
 * single shared navigateToUrl() implementation, so page objects no longer need to duplicate the
 * try/catch/navigateTo navigation logic.
 */
import { BasePage, WebActions } from '@gfk/gta';
import { ResourceManager } from '../../utils/resource-manager';
import { NAVIGATION_TIMEOUT } from '../../constants/timeout-constants';

export class CommonPage {
  protected webActionHandler: WebActions;
  protected resourceManager: ResourceManager;

  constructor(protected basePage: BasePage) {
    this.webActionHandler = basePage.getWebActions();
    this.resourceManager = new ResourceManager({});
  }

  /**
   * Navigates the browser to the specified URL within the given timeout.
   *
   * @param targetUrl - The full URL to navigate to.
   * @param timeout - Optional maximum time to wait for navigation. Defaults to NAVIGATION_TIMEOUT.
   */
  public async navigateToUrl(targetUrl: string, timeout: number = NAVIGATION_TIMEOUT): Promise<void> {
    try {
      await this.webActionHandler.navigateTo(targetUrl, timeout, 'domcontentloaded');
    } catch (navigationError) {
      console.error(`Navigation to URL failed: ${targetUrl}`, navigationError);
      throw navigationError;
    }
  }
}
```

### 3. Omnishopper's pattern for comparison

`config.ts` — single source of the base URL, resolved once via a getter:
```typescript
get BASE_URL() {
  return this.getBaseURL(process.env.ENV || config.ENV);
},
```
(`getBaseURL(env)` looks up a `baseURLs` map keyed by `DEV`/`SI`/`UAT`/`EUSI`/`PROD_*`.)

Spec files then just do:
```typescript
let reportUrl = config.BASE_URL + reportTestData?.navUrlWithDataSetId;
```
— one expression, no independent fallback literal, no ad-hoc normalization.

`CommonTestCase.navigateToUrl()` (the shared method, ~30 classes extend it):
```typescript
public async navigateToUrl(targetUrl: string, timeout: number = NAVIGATION_TIMEOUT): Promise<void> {
  try {
    await this.webActionHandler.navigateTo(targetUrl, timeout, "domcontentloaded");
  } catch (navigationError) {
    console.error(`Navigation to URL failed: ${targetUrl}`, navigationError);
    throw navigationError;
  }
}
```
Plus a higher-level `navigateToReportUrl()` built on top of it that adds a post-navigation Madlib-visibility wait and a one-time retry-on-error-banner.

The documented exception — `FormatPanel` does **not** extend `CommonTestCase`. It's a standalone class with its own `webActionHandler`/`resourceManager`, and its `navigateToUrlAndCheckMadlibVisbility()` calls `this.webActionHandler.navigateTo(...)` directly rather than through any shared `navigateToUrl()`:
```typescript
public async navigateToUrlAndCheckMadlibVisbility(targetUrl: string) {
  await this.webActionHandler.navigateTo(targetUrl, MAX_TEST_TIMEOUT, "domcontentloaded");
  const reportMenuIcon = this.webActionHandler.getWebElement(
    this.resourceManager.getResource("formatPanelId", FP_COMPONENT_NAME)
  );
  await reportMenuIcon.waitFor();
}
```

### 4. Honest assessment

**Two separate things are being compared here, and they land differently:**

- **The "navigate and load" method itself (`navigateToUrl`)**: our `CommonPage.navigateToUrl()` is a verbatim, line-for-line mirror of omnishopper's `CommonTestCase.navigateToUrl()` — same signature, same try/catch, same `webActionHandler.navigateTo(..., 'domcontentloaded')` call, same error re-throw. This part is **already equivalent**, not just similar.

- **Base URL resolution (the actual thing PART 2 was asked about)**: this is **not** equivalent — it's genuinely duplicated, and in the opposite shape from omnishopper. Omnishopper has exactly **one** place (`config.BASE_URL` getter) that resolves the base URL, and every consumer (14+ spec files, `global-setup.ts`) reads that single property. Our repo has **no equivalent single source**: the fallback literal is copy-pasted independently into `playwright.config.ts`, `global-setup.ts`, `start-from-scratch.page.ts`, and `start-with-prompt.page.ts` (4 separate literals that must be kept in sync by hand), and the trailing-slash-normalize + `new URL('survey', ...)` construction is copy-pasted into 3 separate files (`login.page.ts`, `start-from-scratch.page.ts`, `start-with-prompt.page.ts`). `CommonPage` does not own or expose any of this — it only owns the final one-line `navigateTo()` call, exactly like omnishopper's base class, but omnishopper never needed a per-page-object base-URL builder because `config.BASE_URL` already centralizes it upstream in the spec/config layer.

So: **partially there**. The shared navigation *method* is equivalent to omnishopper's. The base-URL *sourcing/construction* that feeds into it is not centralized at all in our repo — it's duplicated per file, which is the same category of problem omnishopper avoided with `config.BASE_URL`, not the same category of problem omnishopper has with `FormatPanel` (that's a "doesn't extend the shared class" gap; ours is a "no shared source of truth for the URL value" gap, existing independently of whether the class extends `CommonPage` or not — `login.page.ts` extends `CommonPage` and still duplicates the URL logic).
