## Blur/Click-Away Fix — 2026-09-30

Actual on-disk locator file is `e2e/locators/survey/surveyBuilder.locator.json`
(not `surveyBuilder.json`).

### Root cause (confirmed via real Codegen recording)

Recorded sequence for adding a Single Choice question with 3 options:

```ts
await page.getByRole('textbox', { name: 'Option 2' }).fill('s');
await page.locator('div').filter({ hasText: /^s$/ }).click(); // blur/click-away
await page.locator('niq-button').filter({ hasText: 'Add option' }).click();
await page.getByRole('textbox', { name: 'Option 3' }).click();
await page.getByRole('textbox', { name: 'Option 3' }).fill('dsdsfdsf');
await page.locator('[data-test-id="-input-checkbox"]').check();
await page.locator('div').filter({ hasText: '1. Add option Required' }).nth(2).click(); // another blur/click-away
await page.locator('[data-test-id="add-question"]').click();
```

This confirms:
1. `addOptionButton` (`niq-button:has-text('Add option')`) is correct as-is — no change needed.
2. `requiredToggle` (`[data-test-id='-input-checkbox']`) is real — the truncated id with no
   prefix is how the live DOM actually renders it (previously flagged UNCONFIRMED/suspicious).
3. The live UI requires clicking a neutral element outside the active input (a blur/click-away)
   before "Add option" or "Add question" become interactable — `fillLabeledField()` never did
   this, which is why `addOptionToQuestion()` was timing out.

The two Codegen blur clicks both used brittle, test-data-dependent locators (`div` filtered by
the literal typed-in text `/^s$/`, and `div` filtered by hard-coded panel text + `nth(2)`) — not
reused as-is, per the instruction to avoid fragile, data-dependent selectors.

### Chosen blur target — confidence level

Proposed and used `surveyBuilderBlurTarget` → the "Build Survey" wizard-step label, via the
Playwright selector `text=Build Survey >> nth=0`.

- This exact text is **already relied upon elsewhere in this codebase** as
  `buildSurveyPageHeading` (`e2e/locators/survey/select-panelist.locator.json`), waited-for and
  asserted `isVisible()` in `SelectPanelistPage.isBuildSurveyPageLoaded()` — a check that is part
  of the currently-passing `@SurveyBuilderSetup` test. So its **presence** on the Build Survey
  page is confirmed.
- Per the page accessibility snapshot captured in the test-failure artifacts
  (`e2e/test-results/.../error-context.md`), the "Build Survey" label (`generic [ref=e70]`) is a
  sibling of the wizard-step `button "Step"` (`ref=e66`), not nested inside it — so clicking the
  label text itself should not trigger the step-navigation button's click handler.
- **Not independently confirmed:** clicking this element specifically for blur purposes has not
  been exercised in a live Codegen capture. If this starts failing, re-check against the live DOM
  — this is flagged as item 6 in the class-level doc comment, following the same convention as
  the other UNCONFIRMED items in this file.

### STEP 2 — `e2e/page-objects/survey/surveyBuilder.page.ts`

**Before:**
```ts
  /** Fills Option N / Row N / Column N fields by their visible role label, e.g. 'Option 1', 'Row 2'. */
  private async fillLabeledField(label: string, value: string): Promise<void> {
    const field = this.webActionHandler.getWebElement(
      this.resourceManager.getDynamicResource('optionInputByLabel', label, SURVEY_BUILDER_PAGE_COMPONENT_NAME)
    );
    await field.waitFor();
    await field.enterText(value);
  }
```

**After:**
```ts
  /** Fills Option N / Row N / Column N fields by their visible role label, e.g. 'Option 1', 'Row 2'. */
  private async fillLabeledField(label: string, value: string): Promise<void> {
    const field = this.webActionHandler.getWebElement(
      this.resourceManager.getDynamicResource('optionInputByLabel', label, SURVEY_BUILDER_PAGE_COMPONENT_NAME)
    );
    await field.waitFor();
    await field.enterText(value);
    await this.blurActiveField();
  }

  /** Clicks a neutral element to blur the currently focused field — required before
   * "Add option"/"Add question" become interactable (per real Codegen recording). */
  private async blurActiveField(): Promise<void> {
    const blurTarget = this.webActionHandler.getWebElement(
      this.resourceManager.getResource('surveyBuilderBlurTarget', SURVEY_BUILDER_PAGE_COMPONENT_NAME)
    );
    await blurTarget.click();
    await this.webActionHandler.delay(UI_STATE_UPDATE_DELAY);
  }
```

Only a **single call site** was added, inside `fillLabeledField()`. This is deliberate, not an
oversight: per the recorded sequence, both blur clicks happened immediately after a field fill —
once after filling Option 2 (before the next `addOptionToQuestion()` call in the loop), and once
after filling Option 3, the last option (before `clickAddQuestion()` is later called by the test).
Since `fillLabeledField()` now blurs after *every* option/row/column fill, both of those real
needs are already covered by this one call site — adding a second, separate blur call before
`clickAddQuestion()` itself would be redundant. `clickAddQuestion()` is invoked by the test files,
not from inside `addSingleChoiceQuestion()`/`addMultipleChoiceQuestion()`, so there was no method
body location to add a second call to in those methods anyway.

`fillQuestionText()` and `setSurveyTitle()` were **not** touched — `TC_BS_02` (survey title) has
already passed without this fix, and nothing in the recording shows a blur being required after
typing the question text itself (only after option fields, right before a button click).
