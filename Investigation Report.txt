## How Playwright's `test.id` is generated (key fact used throughout this review)

Traced through `e2e/node_modules/playwright/lib/common/index.js` (`bindFileSuiteToProject`)
and `e2e/node_modules/playwright-core/lib/coreBundle.js` (`calculateSha1`):

```js
// playwright/lib/common/index.js
const fileId = calculateSha1(toPosixPath(relativeFile)).slice(0, 20);
...
const testIdExpression = `[project=${project.id}]${toPosixPath(file2)}${titles.join("")}`;
const testId = fileId + "-" + calculateSha1(testIdExpression).slice(0, 20);
test.id = testId;

// playwright-core/lib/coreBundle.js
function calculateSha1(buffer) {
  const hash = crypto.createHash("sha1");
  hash.update(buffer);
  return hash.digest("hex");   // <-- lowercase hex digest, nothing else
}
```

`test.id` is therefore **always** of the exact shape `/^[0-9a-f]{20}-[0-9a-f]{20}$/` —
two 20-character lowercase-hex SHA1 slices joined by a single hyphen. It is computed
internally by the Playwright test runner from the test file path + suite/test titles; it
is never read from an HTTP request, CLI flag, or any other externally-supplied string, and
its output alphabet (`0-9a-f-`) structurally cannot contain `/`, `\`, `..`, a null byte, or
an absolute-path prefix. This holds regardless of what characters appear in the *test title*
(the title is hashed, not concatenated raw into the id).

`process.env.__CURRENT_TEST_ID__` (used in base-page-factory.ts) is set by
`lt-session-reporter.ts`'s `onTestBegin` hook (`process.env.__CURRENT_TEST_ID__ = test.id;`) —
i.e., it is this exact same SHA1-hex value, just relayed through an environment variable
for cross-module access within the same Node process, not sourced from outside the process.

## Detailed reasoning per finding

### F1–F3, F8 — globalTeardown.ts static path constants

```ts
const ALLURE_RESULTS_DIR = path.join(process.cwd(), 'allure-results');   // line 6
const ENV_PROPS_PATH = path.join(ALLURE_RESULTS_DIR, 'environment.properties'); // line 7
...
fs.mkdirSync(ALLURE_RESULTS_DIR, { recursive: true });                   // line 48
...
// Safe: ENV_PROPS_PATH uses path.join() with hardcoded directory and filename, no user input
fs.writeFileSync(ENV_PROPS_PATH, envContent, 'utf-8');                   // line 271
```
**Trace:** `process.cwd()` (the process's working directory, set by whoever launches the
test run — a build machine or developer, not an external actor) joined with hardcoded
string literals only. There is no per-test, per-file, or per-request variable in this path
at all. **(d) something else — a build-time constant, not "dynamic input"** in any
meaningful sense. **Verdict: false positive.**

### F4, F5 — mapping-file and Allure-result read loops (globalTeardown.ts)

```ts
// lines 63–68 (test-session mapping files)
const mappingFiles = fs.readdirSync(sessionDir).filter((f) => f.startsWith('test-') && f.endsWith('.json'));
for (const file of mappingFiles) {
  const sanitizedFile = path.basename(file);
  const filePath = path.join(sessionDir, sanitizedFile);
  const data = JSON.parse(fs.readFileSync(filePath, 'utf-8'));
  ...

// lines 88–98 (Allure result files)
const allureFiles = fs.readdirSync(ALLURE_RESULTS_DIR).filter((f) => f.endsWith('-result.json'));
const testResults = allureFiles.map((file) => {
  const sanitizedFile = path.basename(file);
  const filePath = path.join(ALLURE_RESULTS_DIR, sanitizedFile);
  const result = JSON.parse(fs.readFileSync(filePath, 'utf-8'));
  return { filePath, result };
});
```
**Trace:** `file` originates from `fs.readdirSync(sessionDir)` / `fs.readdirSync(ALLURE_RESULTS_DIR)` —
**(a) a filename Node itself discovered by listing an existing, hardcoded-path directory.**
`readdirSync` can only ever return bare filenames that physically exist as directory entries
in that directory (it never returns `../foo` or absolute paths — the OS directory-listing
syscall returns entry names, not arbitrary strings). On top of that, the code additionally
runs every filename through `path.basename()` before use, which is the standard sanitizer
Cycode itself recognizes for this exact rule (see the "Sanitize filename to prevent path
traversal attacks" comment already in the code at line 95). **Verdict: false positive** —
doubly so (safe source + explicit sanitizer).

### F6, F7 — `fs.writeFileSync(testResult.filePath, ...)` (globalTeardown.ts, lines 135 & 242)

```ts
// Safe: testResult.filePath was sanitized with path.basename() during file reading
fs.writeFileSync(testResult.filePath, JSON.stringify(result, null, 2));
```
**Trace:** `testResult.filePath` is exactly the `filePath` constant built in F5 above (same
object, carried through the `testResults` array from the Step-2 `.map()`). No new dynamic
value is introduced here — it's a reuse of an already-sanitized path. **Verdict: false
positive** (inherited sanitization from F5).

### F9, F10, F15, F16, F18, F19 — static session-directory operations

### F11 — `fs.writeFileSync(path.join(sessionDir, \`test-${testId}.json\`), ...)` (base-page-factory.ts, lines 129–137)

```ts
const testId = process.env.__CURRENT_TEST_ID__ || (global as any).__CURRENT_TEST_ID__ || null;
const sessionDir = getLambdaTestSessionDir();
fs.mkdirSync(sessionDir, { recursive: true });
...
if (testId) {
  fs.writeFileSync(
    path.join(sessionDir, `test-${testId}.json`),
    JSON.stringify({ sessionName, timestamp, testId }),
    'utf-8'
  );
  ...
}
```
**Trace:** `testId` comes from **(c) `process.env.__CURRENT_TEST_ID__`** (with an in-process
`global` fallback), which is populated exclusively by `lt-session-reporter.ts`'s
`onTestBegin(test)` hook via `process.env.__CURRENT_TEST_ID__ = test.id;` — i.e. it is
Playwright's own `test.id`, described above (`/^[0-9a-f]{20}-[0-9a-f]{20}$/`, SHA1-hex only).
As established, this format cannot contain `../`, absolute-path segments, or null bytes.
**Verdict: false positive** — the source cannot produce malicious path segments.

However, this is the **one place worth a non-blocking hardening fix**: the sibling file
`lt-session-reporter.ts` (F13/F17) explicitly sanitizes the same kind of value
(`testId.replace(/[^a-zA-Z0-9-]/g, '_')`) before using it in a filename, while this file does
not. Even though `testId` cannot realistically be malicious today, applying the identical
sanitizer here would (1) make the two call sites consistent, (2) satisfy Cycode's pattern
matcher (eliminating the SAST noise for this specific line without behavior change), and
(3) add defense-in-depth in case `__CURRENT_TEST_ID__` is ever set from a different source
in the future. **Proposed diff (not applied):**

```diff
         const testId =
           process.env.__CURRENT_TEST_ID__ || (global as any).__CURRENT_TEST_ID__ || null;
+        const safeTestId = testId ? testId.replace(/[^a-zA-Z0-9-]/g, '_') : null;

         const sessionDir = getLambdaTestSessionDir();
         fs.mkdirSync(sessionDir, { recursive: true });
@@
-        if (testId) {
+        if (safeTestId) {
           fs.writeFileSync(
-            path.join(sessionDir, `test-${testId}.json`),
+            path.join(sessionDir, `test-${safeTestId}.json`),
             JSON.stringify({ sessionName, timestamp, testId }),
             'utf-8'
           );
           console.log(`[LT Session] ✓ test-${testId}.json written`);
```

### F12 — `fs.writeFileSync(path.join(sessionDir, \`worker-${workerIndex}.json\`), ...)` (base-page-factory.ts, lines 143–146)

```ts
const workerIndex = Number(process.env.TEST_WORKER_INDEX || 0);
...
fs.writeFileSync(
  path.join(sessionDir, `worker-${workerIndex}.json`),
  JSON.stringify({ sessionName, timestamp }),
  'utf-8'
);
```
**Trace:** `workerIndex` comes from **(c) `process.env.TEST_WORKER_INDEX`**, but it is passed
through `Number(...)` before use. `Number("../../etc/passwd" || 0)` evaluates to `NaN`, and
`` `worker-${NaN}.json` `` → the literal filename `worker-NaN.json` — not a traversal
sequence. Any non-numeric string collapses to `NaN`; any numeric string becomes a plain
digit sequence. **Verdict: false positive** — numeric coercion neutralizes injection.

### F13, F14 — `path.join(sessionDir, \`test-${testId}.json\`)` read + cleanup (lt-session-reporter.ts, lines 36–52)

```ts
onTestEnd(test: TestCase, result: TestResult) {
  const testId = test.id;
  const sessionDir = getLambdaTestSessionDir();
  const testSessionFile = path.join(sessionDir, `test-${testId}.json`);
  ...
  if (fs.existsSync(testSessionFile)) {
    const data = JSON.parse(fs.readFileSync(testSessionFile, 'utf-8'));
    ...
    try {
      fs.unlinkSync(testSessionFile);
    } catch { /* ignore cleanup failure */ }
  }
```
**Trace:** Here `testId` is **(b) `test.id`, taken directly from the Playwright `TestCase`
object passed into the reporter's `onTestEnd(test, result)` hook** — the most direct possible
source, with no environment-variable relay at all. Same SHA1-hex format guarantee as above.
**Verdict: false positive** for both the read (F13) and the cleanup unlink (F14).

### F17 — mapping-file write with explicit sanitization (lt-session-reporter.ts, lines 104–120)

```ts
fs.mkdirSync(sessionDir, { recursive: true });
// Use a collision-resistant filename per test/process to prevent concurrent write conflicts
const safeTestId = testId.replace(/[^a-zA-Z0-9-]/g, '_');
const mappingFile = path.join(sessionDir, `test-${safeTestId}-${process.pid}-${Date.now()}.json`);
fs.writeFileSync(mappingFile, JSON.stringify({ ... }, null, 2), 'utf-8');
```
**Trace:** `testId` is the same safe `test.id` value as F13, and is **additionally** run
through an explicit allow-list regex sanitizer (`[^a-zA-Z0-9-]` → `_`) before being
interpolated into the filename. `process.pid` and `Date.now()` are both numbers.
**Verdict: false positive** — this is the reference "already sanitized" pattern the rest of
the codebase should be made consistent with (see F11's proposed fix).

---

## Bottom line

All 19 audited call sites are false positives with respect to genuine, attacker-reachable
path-injection risk: every dynamic segment is either directory-listing-derived +
`path.basename()`-sanitized, an explicitly regex-sanitized test id, a `Number()`-coerced
worker index, or Playwright's own SHA1-hex `test.id` (format verified from the installed
`playwright`/`playwright-core` package source, which cannot contain `../`, absolute paths,
or null bytes). No fix is required for correctness/security. One optional, non-blocking
consistency fix is proposed for `base-page-factory.ts` (F11) to mirror the sanitization
already present in `lt-session-reporter.ts` and quiet the recurring SAST noise on that line.
