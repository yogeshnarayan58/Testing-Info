# Dataset Selection Boolean Fix — `searchAndSelectDataset()`

File: [e2e/page-objects/survey/start-from-scratch.page.ts](page-objects/survey/start-from-scratch.page.ts)

## Original Request (verbatim)

> In searchAndSelectDataset() (start-from-scratch.page.ts), fix the return

## Root Cause

All four early-return / final-return branches in `searchAndSelectDataset()` called
`this.isDatasetSelectionConfirmed()`, which only checks the visibility of
`chooseDatasetBreadcrumb` (`[data-test-id='dataset-picker-title']`):

- **Condition 1** already used `chooseDatasetBreadcrumb.isVisible()` as its trigger
  (`!isOnDatasetScreen`). Calling `isDatasetSelectionConfirmed()` afterward re-read the
  exact same element and could only echo the same result — not an independent check.
- **Condition 2** matched selection via `defaultDatasetElement`'s text — an unrelated
  element to `chooseDatasetBreadcrumb`, so the follow-up call added no real verification.
- **Conditions 3 and 4** clicked a dataset tile and then called
  `isDatasetSelectionConfirmed()`, expecting it to confirm the click worked. But that
  method checks whether the **"Choose a dataset" screen itself is still visible** — a
  screen that is expected to disappear/navigate away after a *successful* click. So a
  successful click could make the check return `false` (looking like failure), while a
  no-op could leave the breadcrumb still visible (looking like it "confirmed" nothing
  happened) — the check is inverted/meaningless as a post-click signal.

`isDatasetSelectionConfirmed()` itself was **not deleted** — it's a public method with no
other callers found in the codebase (`grep_search` for `isDatasetSelectionConfirmed`
outside this file returned nothing), but removing it wasn't requested and it may still be
a useful standalone "is the picker screen showing" check for other call sites in the
future.

## Explanation Per Condition

| Condition | Trigger check | Old return | New return | Why |
|---|---|---|---|---|
| 1 | `!chooseDatasetBreadcrumb.isVisible()` | `isDatasetSelectionConfirmed()` (re-reads same element) | `true` | Trigger check already IS the confirmation; re-checking is a no-op that can only repeat the same answer. |
| 2 | `defaultDatasetElement` text includes `datasetLabel` | `isDatasetSelectionConfirmed()` (unrelated element) | `true` | Text match against `defaultDataset` already proves the label is selected; `chooseDatasetBreadcrumb` has nothing to do with that element. |
| 3 | `datasetByLabel` tile already visible → clicked | `isDatasetSelectionConfirmed()` (screen-visibility, inverted after click) | `true` + explicit comment | No resource in `start-from-scratch.locator.json` represents a "tile selected/highlighted" state (only `datasetByLabel`, `defaultDataset`, `chooseDatasetBreadcrumb`, `applyButton`, etc. exist) and confirming a new one requires live DOM inspection not available in this session — flagged as an assumption rather than inventing an unverified locator. |
| 4 | search → `datasetByLabel` tile found → clicked | `isDatasetSelectionConfirmed()` (screen-visibility, inverted after click) | `true` + explicit comment | Same limitation as Condition 3 — no confirmed real post-click signal exists yet without live DOM inspection. |
