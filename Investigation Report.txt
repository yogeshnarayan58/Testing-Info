# Investigation: Path Handling in OmniShopper vs. This Repo (Cycode "Unsanitized dynamic input in file path")

Investigation only — no source files were modified. Repo scanned:
`disc-fe-omnishopper-ui-automation` (external Playwright/TypeScript automation repo).
Compared against the equivalent files already in this repo's `e2e/` tree.

## 1. Summary

OmniShopper's LambdaTest session bookkeeping (`.lt-sessions/`) and Allure result
post-processing use the same dynamic-path shape this repo's Cycode findings are
about: `testId`, `workerIndex`, API-provided session names/IDs, and directory
listings (`readdirSync`) are all interpolated into `path.join(...)` calls that
then feed `fs.readFileSync` / `writeFileSync` / `unlinkSync` sinks.

**Key finding: OmniShopper has no path-safety helper at all.** There is no
`safeJoin`, `sanitizePath`, `assertContainedDir`, or equivalent containment
check anywhere in that repo. The only mitigation present is ad-hoc, inconsistent
input sanitization (regex replace on individual dynamic values) applied at some
call sites but not others, with zero re-verification of the final resolved path
before the filesystem sink. This repo's `e2e/utils/safe-path.ts`
(`safeJoin` + `assertContainedDir`), already used in
[globalTeardown.ts](playwright/setup/globalTeardown.ts),
[lt-session-reporter.ts](playwright/reporters/lt-session-reporter.ts) and
[base-page-factory.ts](utils/base-page-factory.ts), is strictly more defensive
than anything found in OmniShopper. **Do not treat OmniShopper as a source of a
better pattern to copy** — it is evidence of the *unmitigated* version of the
same finding class, useful for illustrating what Cycode is flagging and why
containment checks matter.

## 3. Traced Data Flows (OmniShopper)

### 3a. `lt-session-reporter.ts` — per-test session file (representative example)
```
Dynamic value:      test.id (Playwright TestCase id, framework-controlled but
                     still "external" to this file's own logic)
Validation:          NONE at the write site in onTestEnd():
                       const testSessionFile = path.join(sessionDir, `test-${testId}.json`);
                       fs.existsSync(testSessionFile) / fs.readFileSync(...) / fs.unlinkSync(...)
Path construction:   path.join(process.cwd(), ".lt-sessions") + template-literal filename
Normalization:       NONE (no path.resolve/normalize, no realpath)
Containment check:   NONE — no comparison of the final path against sessionDir
Filesystem sink:     fs.existsSync / fs.readFileSync / fs.unlinkSync directly on the
                     unvalidated joined path
```
Later in the same file (mapping-file write), a sanitizer is applied but only to
the *input*, never to the *resulting path*:
```
const safeTestId = testId.replace(/[^a-zA-Z0-9-]/g, '_');
const mappingFile = path.join(sessionDir, `test-${safeTestId}-${process.pid}-${Date.now()}.json`);
fs.writeFileSync(mappingFile, ...)
```
This is character-allowlisting of one segment, not path containment — it
prevents `../` style traversal in that one value but never verifies the final
resolved path stays under `sessionDir`, and the read path above has no
sanitization at all.

### 3b. `globalTeardown.ts` — directory listing → per-file read/write
```
Dynamic value:      filenames from fs.readdirSync(sessionDir) / readdirSync(ALLURE_RESULTS_DIR)
Validation:          NONE on the loop variable `file` itself
Path construction:   const filePath = path.join(sessionDir, sanitizedFile)
                     where sanitizedFile = path.basename(file)  // applied to filenames
                     already returned by readdirSync (an allowlist would be
                     stronger, since basename() is a no-op for a plain filename
                     with no separators, which is what readdirSync always returns)
Normalization:       NONE beyond path.join
Containment check:   NONE — no check that the joined path is still inside sessionDir/ALLURE_RESULTS_DIR
Filesystem sink:     fs.readFileSync(filePath, ...) then later fs.writeFileSync(testResult.filePath, ...)
```
`readdirSync` entries can't contain `..` as their own segment (the OS won't
return that), so this particular flow is low real-world risk, but the code
provides no structural guarantee of that — it relies on an implicit assumption
about `readdirSync` behavior rather than an explicit containment check.

### 3c. `base-page-factory.ts` — worker/session bookkeeping
```
Dynamic value:      process.env.TEST_WORKER_INDEX (Number(...), no NaN guard),
                     process.env.__CURRENT_TEST_ID__ / global.__CURRENT_TEST_ID__
Validation:          NONE — Number(process.env.TEST_WORKER_INDEX || 0) is used directly
                     in `worker-${workerIndex}.json` even if it evaluates to NaN
Path construction:   path.join(sessionDir, `worker-${workerIndex}.json`),
                     path.join(sessionDir, `test-${testId}.json`)  (testId itself unsanitized here)
Normalization:       NONE
Containment check:   NONE
Filesystem sink:     fs.appendFileSync / fs.writeFileSync
```

### 3d. `common-test-case.ts` — baseline screenshot path
```
Dynamic value:      reportName, browserName, testCaseName, environment (all function params)
Validation:          regex allowlist per segment: .replace(/[^a-zA-Z0-9-_]/g, "-")
Path construction:   path.join("baseline-screenshots", sanitizedReportName, sanitizedBrowserName,
                     datasetShort, sanitizedEnvironment, `${sanitizedTestCaseName}.png`)
Normalization:       NONE (no path.resolve after join)
Containment check:   NONE — never verifies the joined path is still under "baseline-screenshots/"
Filesystem sink:     (screenshot write, further down in the same method, via Playwright's page.screenshot)
```
This is the closest OmniShopper comes to "good" sanitization (per-segment
character allowlisting on every dynamic input before use), but it still stops
at input sanitization and never re-validates the constructed path itself.

## 4. Comparison Against This Repo's `safe-path.ts` Pattern

This repo's [utils/safe-path.ts](utils/safe-path.ts) (already in the current
selection) does what OmniShopper's code never does — it performs the full
five-stage flow requested by this investigation:

1. **Validation** — rejects segments containing `..`, `~`, `\`, absolute paths,
   Windows drive/UNC forms, empty strings, and null bytes, *before* any join.
2. **Sanitization** — allowlists each segment to `[a-zA-Z0-9_.-]`, rejecting
   degenerate results (empty or all-underscore).
3. **Path construction** — `path.join(realBaseDir, ...sanitizedSegments)` only
   after both of the above pass.
4. **Normalization/resolution** — `fs.realpathSync` on the base dir (symlink
   resolution) plus `path.resolve`/`path.normalize` on the joined result.
5. **Containment check** — explicit `startsWith(baseDirWithSeparator)` (or
   exact-match) verification before the path is ever returned to a caller,
   throwing otherwise.

`assertContainedDir` provides the same containment guarantee for directories
obtained indirectly (e.g. `getLambdaTestSessionDir()`), and the consuming
files ([globalTeardown.ts](playwright/setup/globalTeardown.ts),
[lt-session-reporter.ts](playwright/reporters/lt-session-reporter.ts),
[base-page-factory.ts](utils/base-page-factory.ts)) additionally re-derive and
re-check the path immediately before each individual `fs.*` sink call (see
`sanitizeFilePath()` in `lt-session-reporter.ts`), plus enforce filename-shape
regexes (`MAPPING_FILENAME_RE`, `ALLURE_RESULT_FILENAME_RE`) and extension
checks (`.endsWith('.json')`) as defense-in-depth beyond what OmniShopper does
anywhere.

| Aspect | OmniShopper | This repo (`safe-path.ts` + call sites) |
|---|---|---|
| Dedicated helper | None found | `safeJoin` / `assertContainedDir` |
| Input character allowlisting | Partial, inconsistent (present in `common-test-case.ts`, absent in most `.lt-sessions` read paths) | Consistent, centralized in `safeJoin` |
| Traversal/absolute-path pre-checks | None | Explicit (`..`, `~`, `\`, `isAbsolute`, UNC/drive regex) |
| Symlink resolution | None | `fs.realpathSync` on base dir |
| Post-join containment verification | None anywhere | Enforced in helper + re-checked at each sink |
| Filename-shape/extension allowlisting at sink | None (some `readdirSync` filters use `startsWith`/`endsWith`) | Regex full-match allowlists + `.json` extension guard |

## 5. Conclusion / Evidence for the Cycode Finding

OmniShopper's code is a real-world illustration of exactly the pattern Cycode
flags as "Unsanitized dynamic input in file path": dynamic values
(`testId`, `workerIndex`, API session data, directory-listing filenames) reach
`fs.*` sinks via `path.join` with no post-construction containment check, and
in several call sites (the read/delete paths in `lt-session-reporter.ts`,
`global-setup.ts`'s cleanup loop, `base-page-factory.ts`'s `worker-*`/`test-*`
writes) with no input sanitization either. It is useful only as a negative
example — confirmation of what an *unmitigated* version of this finding looks
like — not as a source of a stronger fix. This repo's existing `safe-path.ts`
already implements a stricter, five-stage validate → sanitize → construct →
normalize → contain pattern than anything present in OmniShopper, and should
remain the reference implementation for addressing the Cycode finding here.
