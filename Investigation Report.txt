## Pre-implementation DOM confirmation (required before Part 1)

Before touching `searchAndSelectDataset()`, confirmed whether `start-with-prompt`'s dataset
screens have equivalents of `defaultDataset` (`[data-test-id='rv-default-dataset']`) and
`chooseDatasetBreadcrumb` (`[data-test-id='dataset-picker-title']`), which only existed in
`start-from-scratch.locator.json` beforehand.

Evidence (via `node_modules/@nielsen/crf-rv-common/esm2022/lib/components/dataset-selector/dataset-selector.component.mjs`):

- Both flows' existing locator files already shared **identical** `data-test-id`s for other
  controls on this screen — `btn-next-dataset` (`nextButton` / `nextDatasetButton`),
  `dataset-picker-search-bar-toggle-search-button-icon` / `dataset-picker-search-bar-input`
  (`searchToggle`/`searchInput` vs `datasetSearchToggle`/`datasetSearchInput`), and
  `apply-dataset-btn` (`applyButton` vs `applyDatasetButton`) — all found in the exact same
  `dataset-selector.component.mjs` template, confirming **both flows render the same shared
  Angular component** for dataset selection, not two separate implementations.
- Grepping that same component file confirmed it also unconditionally renders
  `data-test-id="dataset-picker-title"` (title/breadcrumb, gated only on
  `!isLoading && datasets?.length > 0 && !isSearchOpen && ...`, not on flow type) and
  `data-test-id="rv-default-dataset"` (default dataset tile, gated only on
  `filteredDefaults?.[0]`, not on flow type).

Conclusion: both elements exist on the start-with-prompt flow's dataset screens because it's
the same shared component instance — implementation proceeded.

```jsonc

{ "elementName": "defaultDataset", "selectorType": "css", "selectorValue": "[data-test-id='rv-default-dataset']" }
```

`searchAndSelectDataset()` return type changed `Promise<void>` → `Promise<boolean>` and now
follows the same fallback chain as `start-from-scratch.page.ts`'s fixed version, using this
file's own resource names:

1. `chooseDatasetBreadcrumb` not visible → already past this screen → `return true` (no
   further checks; this is the terminal case for that branch, not re-verified).
2. `defaultDataset` text already includes `datasetLabel` → `return true`.
3. `datasetByText(datasetLabel)` already visible (no search needed) → click it →
   `return true` (no re-check of the click; a real action just happened, trusted directly,
   consistent with the reference implementation).
4. Otherwise: toggle search → enter `searchTerm` → click `datasetByText(datasetLabel)` →
   `return true`.

No branch re-verifies using the exact condition that already triggered it (e.g. branch 1
does not re-check breadcrumb visibility after returning).

**Files:** [`e2e/locators/survey/start-with-prompt.locator.json`](./locators/survey/start-with-prompt.locator.json),
[`e2e/page-objects/survey/start-with-prompt.page.ts`](./page-objects/survey/start-with-prompt.page.ts)

New locators:

```jsonc
{ "elementName": "promptTextarea", "selectorType": "css", "selectorValue": "textarea.prompt-input" },
{ "elementName": "generateSurveyButton", "selectorType": "css", "selectorValue": "[data-test-id='proceed-to-survey']" }
```

Confirmed both from library source (`libs/survey-mod-lib/src/lib/features/select-panelist/components/select-panelist.component.html`):

```html
<textarea class="prompt-input" ... [(ngModel)]="userPrompt" (ngModelChange)="onPromptInput()"></textarea>
...
<button class="next" data-test-id="proceed-to-survey"
  [disabled]="!selectedResponses || (surveyCommonService.flowType().arthur && (!userPrompt.trim() || isPromptSettling()))"
  (click)="proceedToSurveyBuilder()">
  {{surveyCommonService.flowType().arthur ? 'Generate Survey' : 'Proceed to survey builder'}}
</button>
```

— the **same button element** used by the scratch flow's "Proceed to survey builder"
(`select-panelist.locator.json`'s `proceedToSurveyBuilderButton`, a text selector), just with
different text/disabled-condition in the `arthur` (prompt) flow. `generateSurveyButton` is a
separate, `data-test-id`-based locator from `proceedToSurveyBuilderButton` since the visible
text differs between flows.

New method `fillPromptAndGenerate(promptText: string): Promise<void>`:

```ts
async fillPromptAndGenerate(promptText: string): Promise<void> {
  try {
    const promptTextarea = this.webActionHandler.getWebElement(
      this.resourceManager.getResource('promptTextarea', START_WITH_PROMPT_PAGE_COMPONENT_NAME)
    );
    await promptTextarea.waitFor(SMALL_TIMEOUT);
    await promptTextarea.enterText(promptText);

    const generateSurveyButton = this.webActionHandler.getWebElement(
      this.resourceManager.getResource('generateSurveyButton', START_WITH_PROMPT_PAGE_COMPONENT_NAME)
    );
    await generateSurveyButton.waitForEnabled(ELEMENT_WAIT_TIMEOUT);
    await generateSurveyButton.click();
  } catch (error) {
    throw new Error(`Failed to fill prompt and generate survey: ${error instanceof Error ? error.message : error}`);
  }
}
```

Confirmed the button's real disabled condition from `select-panelist.component.ts`:
`isPromptSettling` is a `toSignal` over `promptInput$.pipe(switchMap(() => concat(of(true), timer(1500).pipe(map(() => false)))))`
— i.e. a genuine **~1500ms debounce** after each prompt change, during which the button stays
disabled even with a non-empty prompt and a selected response count.

`@gfk/gta`'s `WebElement` (`e2e/node_modules/@gfk/gta/dist/core/web/webElement.d.ts`) exposes
a **real** `waitForEnabled(timeout?: number): Promise<void>` primitive (polls `isEnabled()`),
so this was used directly instead of a blind delay — `UI_STATE_UPDATE_DELAY` (300ms) alone
would not reliably outlast the 1500ms debounce, so the fallback-delay path described in the
request was not needed here.
